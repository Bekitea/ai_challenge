# BACKLOG

Известные несоответствия и потенциальные баги, обнаруженные при работе с приложением. **Не исправлять без явного указания
пользователя** (см. `AGENTS.md`).

## 1. Память задачи извлекается при выходе из чата вопреки порогу ходов

- **Где**: `core/domain/entities/agent.py` (`update_task_memory`), `core/presentation/cli/cli_app.py` (сохранение памяти
  при возврате в меню), `core/tests/cli_tests/test_uc022_task_memory.py::test_tc_143`.
- **Симптом**: `TASK_MEMORY_UPDATE_EVERY_N_MESSAGES` управляет обновлением
  памяти задачи *во время* хода, но при выходе из чата (`/menu`) память
  извлекается и сохраняется всегда. В результате `/info` до порога её не
  показывает, а персистентное состояние после завершения процесса уже
  содержит цель/ограничения/термины.
- **Следствие**: вывод CLI и сохранённое состояние расходятся; `test_tc_143`
  вынужден проверять только вывод `/info`, а не ground truth.
- **Возможное направление**: либо не извлекать память при выходе, если порог не
  достигнут, либо документировать такое поведение как ожидаемое.

## 2. Ветка чата получает память задачи после выхода, хотя на уровне логики — нет

- **Где**: `core/domain/entities/agent.py` (ветвление агента), сохранение памяти при выходе,
  `core/tests/cli_tests/test_uc022_task_memory.py::test_tc_144`,
  `core/tests/core_tests/test_task_memory.py::test_branch_does_not_copy_task_memory`.
- **Симптом**: unit-тест утверждает, что ветка не наследует память задачи
  (`test_branch_does_not_copy_task_memory`), однако в e2e после создания ветки
  и выхода из чата ветка получает собственную память задачи — она извлекается
  из скопированной при ветвлении истории.
- **Следствие**: свойство «ветка чиста по памяти задачи» невозможно проверить
  по постфактум-состоянию завершённого процесса; e2e и unit-тесты расходятся.
- **Возможное направление**: определиться с целевым поведением и согласовать
  e2e/unit тесты; при необходимости — не запускать извлечение памяти для
  неактивных/веточных чатов при выходе.

## 3. MCP-серверы падают с `ImportError MCPServer` в контейнере

- **Где**: `mcp/time_mcp.py`, `mcp/open_alex_mcp.py`,
  `core/tests/cli_tests/test_uc019_tc101_110_mcp_menu.py`,
  `mcp/tests/test_time_mcp.py`, `mcp/tests/test_open_alex_mcp.py`.
- **Обновление**: в pytest-обёртках `mcp/tests/` добавлен `pytest.skip`, если
  сервер не спавнится (в контейнере — `ImportError MCPServer`); при недоступности
  сети сетевой кейс OpenAlex также скипается.
- **Симптом**: в контейнерной среде `mcp/*_mcp.py` завершаются с
  `ImportError: MCPServer` (класс недоступен/не тот пакет). Из-за этого e2e
  тесты, требующие живого подключения к MCP (TC-103/104/105/109), пропускаются
  (`pytest.skip`).
- **Следствие**: подключение MCP-серверов не покрыто e2e в CI/контейнере;
  проверяется только «чёрный ящик» меню и ошибочные ветки.
- **Возможное направление**: починить импорт/зависимость MCP SDK в окружении
  или скорректировать `core/infrastructure/mcp/mcp_registry.py`/скрипты серверов, после чего включить
  пропущенные тесты.

## 4. Периодические задачи Celery временно законсервированы (нужна переработка)

- **Где**: `core/presentation/celery/celery_app.py` (`SCHEDULED_REPORTS`, `CELERY_BEAT_SCHEDULE`),
  `core/presentation/celery/tasks.py` (`run_agent_report`),
  `core/application/use_cases/run_scheduled_agent_task.py`
  (`RunScheduledAgentTaskUseCase`, DTO `ScheduledReport`), `config.py`
  (`SCHEDULED_REPORTS_ENABLED`, `DEFAULT_REPORT_*`, `CELERY_*`),
  `docker-compose.yml` (сервисы `worker`/`beat`).
- **Текущее состояние**: функция **отключена флагом**. `config.SCHEDULED_REPORTS_ENABLED`
  по умолчанию `false`; при выключенном флаге `CELERY_BEAT_SCHEDULE` пуст и
  `beat` ничего не диспатчит, хотя `worker`/`beat` и весь код задачи, реестр
  отчётов и use case сохранены без изменений. Для возврата достаточно выставить
  `SCHEDULED_REPORTS_ENABLED=true`.
- **Симптом/почему мешает**: при включённом расписании `beat` безусловно
  планирует каждый отчёт раз в минуту (`timedelta(minutes=1)`), а
  `RunScheduledAgentTaskUseCase` на каждый запуск создаёт **новый чат**. В
  результате `./data/agents.db` растёт без ограничений, а LLM и MCP-серверы
  постоянно нагружаются — это мешает основной работе (особенно при
  `docker compose up`, где `worker`/`beat` поднимаются всегда).
- **Направление переработки** (сделать, когда функция снова понадобится):
  1. Планирование opt-in и настраиваемое: включение per-report, отдельная
     частота на отчёт (из конфига/БД) вместо жёсткого «раз в минуту».
  2. Жизненный цикл чатов отчётов: сейчас unbounded «новый чат на каждый
     запуск»; нужна политика ретеншна/TTL или контролируемое переиспользование.
  3. Runtime-управление реестром: добавлять/приостанавливать/удалять отчёты
     из конфига или БД и через CLI/UI, а не править статический `dict` в коде.
  4. Наблюдаемость: статус прогонов, расход токенов, ошибки (сейчас виден
     только ответ в логе воркера и результат в result backend).
  5. Провайдер/модель на конкретный отчёт через DTO, а не глобальные
     `DEFAULT_REPORT_PROVIDER`/`DEFAULT_REPORT_MODEL`.
  6. Учесть хранение MCP-соединений in-process (ограничение «ровно один
     воркер»): при нескольких воркерах живые подключения после перезапуска
     «протухают».
- **Действие до переработки**: не включать `SCHEDULED_REPORTS_ENABLED`; код не
  удалять.
