Консольное приложение для взаимодействия с AI агентами.

- **[CLI Specification](docs/cli_spec.md)** - Спецификация интерфейса CLI и индекс use cases
- **[Use Cases](docs/uc/)** - По одному use case на файл: альтернативные потоки и связанные test cases

## Установка

### 1. Клонирование и зависимости

```bash
cd /path/to/project
pip install -r requirements.txt
```

### 2. Настройка переменных окружения

Создайте файл `.env` в корне проекта:

```env
YANDEX_CLOUD_API_KEY=your_api_key_here
YANDEX_CLOUD_FOLDER=your_folder_id_here
```

### 3. Инициализация базы данных

Для создания таблиц в SQLite используйте Alembic миграции:

```bash
# Создать начальную миграцию (автоматически по моделям)
alembic revision --autogenerate -m "Initial migration"

# Применить миграции (создать таблицы)
alembic upgrade head
```

### 4. Запуск приложения

```bash
python main_cli.py
```

## REST API + Web UI (FastAPI + React)

Помимо CLI, приложение умеет поднимать веб-интерфейс: FastAPI отдаёт REST
API (`/api/*`) и собранный React-фронт на одном порту **8080**.

### Режим `LOCAL`

Для локального запуска (например, только с локальной моделью Ollama) есть
режим `APPLICATION_MODE=LOCAL`: ключи Yandex Cloud **не обязательны**, данные
хранятся в отдельной папке `./local-data/`. Провайдер Yandex регистрируется
только при наличии ключей, Ollama — всегда.

### Сборка фронтенда

```bash
cd frontend
npm install
npm run build      # создаёт frontend/dist, который раздаёт FastAPI
```

### Запуск

```bash
python main_api.py
```

По умолчанию поднимается в режиме `APPLICATION_MODE=LOCAL` (Ollama; ключи
Yandex не обязательны; данные в `./local-data/`) и раздаёт и API, и фронт на
одном порту. Откройте <http://127.0.0.1:8080>, создайте чат, выберите локальную
модель и напишите сообщение.

### Авторизация по API-ключу

Все эндпоинты `/api/*`, кроме `/api/health`, требуют действующий API-ключ:

```
Authorization: Bearer <ключ>
```

Ключи выпускаются и отзываются только через CLI: главное меню → `6. API-ключи`
(см. [UC-025](docs/uc/uc-025-manage-api-keys.md)). Секрет показывается **один
раз** при создании; в БД хранится только его SHA-256-хеш, прочитать ключ
повторно нельзя. Веб-UI при первом открытии спрашивает ключ и хранит его в
`localStorage` браузера. Без ключа все защищённые запросы получают HTTP 401.

Переопределяется переменными окружения: `APPLICATION_MODE` (`LOCAL`/`PROD`/`TEST`),
`API_HOST` (по умолчанию `127.0.0.1`), `API_PORT` (по умолчанию `8080`). Для
`PROD`, например:

```bash
APPLICATION_MODE=PROD API_HOST=0.0.0.0 python main_api.py
```

> **ВАЖНО:** ровно **один воркер**. MCP-подключения хранятся в памяти процесса,
> а хранилище — SQLite; несколько воркеров их разорвут.
>
> Схема БД при старте догоняется автоматически (добавляются недостающие колонки),
> поэтому старая БД не ломается при обновлении моделей.
>
> Стриминг ответа пока не поддерживается — ответ приходит целиком.

Для разработки фронта можно запустить Vite-дев-сервер (`cd frontend && npm run dev`,
порт 5173, проксирует `/api` на `:8080`) вместо сборки.

## Запуск всего проекта через Docker Compose

Один `docker compose up` поднимает все сервисы проекта: фронтенд, REST API,
реранкер, Redis и Celery (worker + beat).

### Что поднимается и куда стучаться

| Сервис                | Адрес на хосте                    | Назначение                                             |
| --------------------- | --------------------------------- | ------------------------------------------------------ |
| Фронтенд (nginx)      | <http://localhost:3000>           | Web UI; проксирует `/api` на `web`                     |
| REST API              | <http://localhost:8080/api>       | API (нужен `Authorization: Bearer <ключ>`)             |
| Проверка API          | <http://localhost:8080/api/health>| Публичный health-check                                 |
| Реранкер              | <http://localhost:18080/health>   | HTTP-сервис `bge-reranker-v2-m3` (TEI-совместимый)     |
| Redis / Ollama        | внутри сети                       | Redis для Celery; Ollama — на хосте, порт не публикуем |

**Открывать нужно фронтенд — <http://localhost:3000>.** Запросы к API он
проксирует сам на `web:8080`, поэтому в браузере всё на одном origin и
`Authorization`-заголовок проходит без CORS.

### Предусловия

- Docker Desktop (Compose v2).
- Ollama, запущенная **на хосте** (порт 11434) — контейнера Ollama в compose нет,
  приложение обращается к хосту через `host.docker.internal:11434` и использует
  уже скачанные модели, ничего не дублируется.
- Файл `.env` в корне с ключами Yandex Cloud (режим `PROD` их требует):
  `YANDEX_CLOUD_API_KEY`, `YANDEX_CLOUD_FOLDER`. Compose читает его как
  `env_file` (если файла нет — сервис `web` упадёт при старте с понятной ошибкой).

### Запуск

```bash
docker compose up --build
```

Остановка (данные сохраняются в `./data`):

```bash
docker compose down
```

> Первый старт `reranker` скачивает модель (~2.3 ГБ) в volume `reranker_models`;
> это может занять несколько минут. `web` при этом уже доступен.
>
> Данные (`./data/agents.db`, файловое хранилище, память) монтируются с хоста,
> поэтому CLI, запущенный на хосте, и контейнеры видят одну и ту же БД.

### Первый запуск: создать API-ключ

API закрыт по ключу, поэтому до первого входа в веб-UI нужно выпустить ключ
через CLI (главное меню → `6. API-ключи`). Проще всего — прямо в контейнере:

```bash
docker compose exec -it web python main_cli.py
```

Скопируйте показанный один раз ключ (`aic_...`), откройте
<http://localhost:3000> и вставьте его в поле «Доступ к API». Затем попробуйте:

```bash
curl -i http://localhost:8080/api/models                       # 401 без ключа
curl -H "Authorization: Bearer aic_..." http://localhost:8080/api/models
```

### Отдельные части

- Только реранкер (как раньше, без остальных сервисов):
  `cd reranker_service && docker compose up --build`.
- Compose для контейнера разработки opencode переименован в
  `docker-compose.opencode.yml`.

## Периодические задачи (Celery)

Для работы периодических отчётов агентов требуются Redis, Celery worker и Celery beat.

### 1. Запуск Redis (через Docker)

```bash
docker run -d --name redis-celery -p 6379:6379 redis:alpine
```

### 2. Запуск Celery worker

В отдельном терминале из корня проекта:

```bash
celery -A celery_app worker --loglevel=info --pool=solo
```

> Флаг `--pool=solo` обязателен на Windows, так как Celery не поддерживает там пулы `prefork`/`gevent`.

### 3. Запуск Celery beat (планировщик)

В ещё одном отдельном терминале:

```bash
celery -A celery_app beat --loglevel=info
```

После запуска всех процессов периодические задачи будут выполняться по расписанию, заданному в `celery_app.py`.

## Реранкинг (RAG)

Для переупорядочивания найденных RAG-чанков по релевантности используется
кросс-энкодер `bge-reranker-v2-m3` на CPU. Модель работает в **отдельном
HTTP-сервисе** (`reranker_service/`, Python 3.12 + torch/sentence-transformers),
поэтому основное приложение (Python 3.14/Alpine) не тянет torch и общается с
ним по TEI-совместимому эндпоинту `POST /rerank`.

### Запуск сервиса (Docker)

```bash
cd reranker_service
docker compose up --build
```

Сервис слушает `http://127.0.0.1:18080` (порт `18080`, чтобы не конфликтовать с
часто занятым `8080`). На Windows запускайте тот же `docker compose` через
Docker Desktop и обращайтесь по `127.0.0.1`, а не `localhost`: `localhost`
резолвится в `::1` и может попасть в чужой процесс на том же порту. При первом
старте модель (~2.3 ГБ) скачивается в volume `reranker_models`; чтобы «запечь»
её в образ для офлайн-работы, передайте
`--build-arg PREFETCH_MODEL=BAAI/bge-reranker-v2-m3`.

Проверка:

```bash
curl http://127.0.0.1:18080/health
curl -X POST http://127.0.0.1:18080/rerank \
  -H "Content-Type: application/json" \
  -d '{"query": "capital of France", "texts": ["Paris is the capital", "Cats are pets"]}'
```

### Настройка приложения

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `RERANKER_ENABLED` | `true` | Глобальный выключатель реранкинга |
| `RERANKER_BASE_URL` | `http://127.0.0.1:18080` | Адрес сервиса реранкинга |
| `RERANKER_MODEL_NAME` | `bge-reranker-v2-m3` | Имя модели (информационно) |
| `RERANKER_BATCH_SIZE` | `32` | Размер батча |
| `RERANKER_TIMEOUT` | `60` | Таймаут HTTP-запроса, с |
| `RERANKER_RETRY_COUNT` | `1` | Число повторов при ошибке |

Реранкинг включён по умолчанию для каждого чата. Управление — командой в чате:
`/rerank on`, `/rerank off`, bare `/rerank` показывает состояние (оно также
видно в `/rag` и `/settings`). Если сервис недоступен, RAG-поиск деградирует к
векторному порядку (circuit breaker отключает повторные попытки до перезапуска
процесса). В `APPLICATION_MODE=TEST` используется `MockRerankerProvider` без
сети, поэтому e2e-тесты не требуют запущенного сервиса.

### Порог релевантности и источники

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `RAG_RELEVANCE_THRESHOLD` | `0.3` | Минимальная релевантность чанка в шкале `[0..1]` |

Релевантность считается в единой шкале: при реранкинге — score кросс-энкодера,
при векторном поиске — `1 - vector_distance / 2`. Чанки ниже порога
отбрасываются; если после фильтрации не осталось ни одного, ассистент обязан
ответить «Не знаю» и попросить уточнить вопрос. После каждого ответа в чате с
подключёнными базами CLI печатает блок `[Источники]:` с именем файла, id чанка,
номером фрагмента, релевантностью и короткой цитатой. Подробности — в
[`docs/uc/uc-021`](docs/uc/uc-021-rag-sources-and-relevance-threshold.md).

## Руководство для новых разработчиков

### Архитектурные принципы

#### Чистая архитектура
Приложение построено по принципу **чистой архитектуры** с четким разделением ответственности между слоями. Это обеспечивает тестируемость, поддерживаемость и независимость слоев друг от друга. Но слой домена у нас пока не выделен (вся бизнес логика пока в слое приложения, то есть знает об API инфраструктуры).

#### Инкапсуляция сохранения состояния агента
**Важное архитектурное решение:** Логика сохранения состояния агента инкапсулирована в самом классе `Agent`, а не в use cases или репозиториях.

**Принципы:**
1. **Агент отвечает за своё состояние** — класс `Agent` содержит метод `save()`, который вызывается автоматически при изменениях
2. **Автосохранение по умолчанию** — параметр `auto_save=True` включен для всех агентов
3. **Use cases не управляют сохранением** — бизнес-логика use cases не должна содержать явных вызовов `repository.update_agent()`
4. **Репозиторий предоставляет механизм, агент решает когда использовать** — репозиторий хранит метод `update_agent()`, но вызывает его сам агент через `self._repository.update_agent(self)`

**Когда агент сохраняется автоматически:**
- При изменении настроек (`update_settings()`)
- После каждого сообщения в диалоге (`continue_dialog()`)
- При необходимости можно вызвать `save()` вручную

**Преимущества такого подхода:**
- ✅ Единая точка ответственности за сохранение
- ✅ Use cases остаются чистыми от инфраструктурных деталей
- ✅ Легче тестировать
- ✅ Соответствует принципу инкапсуляции: объект сам управляет своим состоянием

```
┌─────────────────────────────────────────────────────────┐
```

### Модули приложения

#### 1. `main_cli.py` — Точка входа
**Ответственность:**
- Установка переменной окружения `APPLICATION_MODE`
- Вызов фабрики для инициализации компонентов
- Создание CLI приложения и передача ему use cases
- Обработка глобальных исключений

**Важно:** Этот модуль не содержит никакой бизнес-логики.

#### 2. `app_factory.py` — Фабрика приложений
**Ответственность:**
- Определение режима работы через `app_mode` (production/test)
- Валидация переменных окружения для production режима
- Создание реестра LLM провайдеров (`LlmProviderRegistry`)
- Инициализация репозиториев
- Создание всех use cases и возврат их в `UseCasesBundle`

**Ключевой принцип:** CLI слой не знает о режимах работы — фабрика инкапсулирует эту логику.

#### 3. `cli_app.py` — CLI слой представления
**Ответственность:**
- Отображение меню, форм, результатов пользователю
- Сбор ввода пользователя
- Вызов методов use cases для выполнения действий
- Форматирование и вывод результатов

**Зависимости:** Только `use_cases` (DTO и `UseCasesBundle`) плюс модуль констант
`config` и stdlib. Не импортирует:
- Репозитории (`storage.*`)
- LLM провайдеры (`llm_providers.*`)
- Бизнес-объекты (`agents.*`), стратегии (`context_strategies.*`), реестр MCP (`mcp_registry.*`)
- Режимы приложения (`app_mode.*`)
- Фабрику (`app_factory.*`)

**DTO-only:** слой представления никогда не видит бизнес-объект `Agent`. Он хранит
только `agent_id`/`chat_id` и обменивается с use cases исключительно DTO, определёнными
в `use_cases.py`. Use case сам загружает агента внутри по `agent_id`. Это правило
распространяется и на будущий REST API слой.

#### 4. `use_cases/__init__.py` — Слой бизнес-логики
**Ответственность:**
- Инкапсуляция всей бизнес-логики приложения
- Координация между репозиториями, агентами и провайдерами
- Предоставление чистого интерфейса для CLI слоя

**Важно:** Использует напрямую API агента, репозиториев, провайдеров и так далее. Use cases могут зависеть от репозиториев и LLM провайдеров, но CLI слой об этом не знает.

#### 5. `storage/` — Слой доступа к данным
**Модули:**
- `db_connection.py` — управление соединениями с базой данных (инфраструктурный класс)
- `agent_repositories.py` — репозиторий для агентов (CRUD операции)
- `chat_storage.py` — хранение истории чатов
- `orm_models.py` — SQLAlchemy модели для базы данных

**Важно:** Репозитории не должны знать о соединениях с БД. Они получают фабрику сессий как внешнюю зависимость. Управление подключениями инкапсулировано в классе `DatabaseConnection`.

#### 6. `llm_providers.py` — LLM провайдеры
**Реализации:**
- `YandexCloudLlmProvider` — production провайдер для Yandex Cloud API (OpenAI-совместимый)
- `OllamaLlmProvider` — локальные модели Ollama (OpenAI-совместимый `/v1`)
- `MockLlmProvider` — тестовый провайдер для e2e тестов (с настраиваемым именем)
- `LlmProviderRegistry` — реестр именованных провайдеров; агрегирует список
  моделей (`list_models`) и разрешает провайдера по `AgentSettings.provider`

Модели не хардкодятся: список для UI формируется динамически (UC-023). У каждой
модели в списке указан провайдер, поскольку одна и та же модель может
предоставляться разными провайдерами. Провайдер по умолчанию для чатов
отсутствует — пользователь выбирает модель всегда.

#### 6.1. RAG-провайдеры
- `embedding_providers.py` — `OllamaEmbeddingProvider` (эмбеддинги через Ollama)
- `reranker_providers.py` — `HttpRerankerProvider` (HTTP-сервис `reranker_service/`),
  `MockRerankerProvider` (тестовый режим)
- `reranker_service/` — отдельный CPU-контейнер с моделью `bge-reranker-v2-m3`
  (см. раздел «Реранкинг (RAG)»)

#### 6.2. `llm_gateway/` — единый шлюз к Ollama
Ollama плохо переносит параллельные запросы, а приложение нагружает её из
нескольких потоков (CLI, REST API, Celery) и в будущем — из сабагентов.
`llm_gateway/` — отдельный сервис (Python 3.14), который является
**единственным**, кто ходит в Ollama напрямую. Он принимает
Ollama-совместимые запросы (`POST /v1/chat/completions`, `POST /api/embed`,
`GET /api/tags`) и сериализует их через очередь (Redis Streams, durable):
одновременно в Ollama уходит ровно один запрос, остальные ждут.

Основной бэкенд не меняется кодом провайдеров: `OllamaLlmProvider` и
`OllamaEmbeddingProvider` по-прежнему работают по OpenAI/Ollama-API, но их
базовые URL при `LLM_GATEWAY_ENABLED=true` указывают на gateway
(`OLLAMA_NATIVE_BASE_URL`, `OLLAMA_OPENAI_BASE_URL`, `EMBEDDING_BASE_URL`).
В `APPLICATION_MODE=TEST` gateway выключен (там `MockLlmProvider`).

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `LLM_GATEWAY_ENABLED` | `false` | Глобальный выключатель шлюза |
| `LLM_GATEWAY_URL` | `http://127.0.0.1:18081` | Адрес gateway для бэкенда |
| `LLM_GATEWAY_REDIS_URL` | пусто (in-process) | Redis-очередь gateway |
| `QUEUE_WAIT_TIMEOUT` | `600` | Ожидание ответа в HTTP-слое gateway |
| `LLM_UPSTREAM_TIMEOUT` | `300` | Таймаут запроса к Ollama |
| `MAX_QUEUE_DEPTH` | `200` | Backpressure: переполнение → 503 |
| `LLM_REQUEST_TIMEOUT` | `900` | Таймаут чат-запроса (должен перекрывать очередь) |

При недоступности gateway/Redis — **fail fast** (503/504), без обхода в
Ollama. Держать ровно **одну реплику** gateway: гарантия «один запрос в
Ollama» держится на единственном потребителе очереди. Тесты:
`poetry run pytest llm_gateway/tests -v`.

#### 7. `agents.py` — Бизнес-объекты
Эти классы тоже относятся к бизнес-логике приложения, они могут напрямую использовать API репозиториев, провайдеров и так далее.
**Классы:**
- `Agent` — основной класс агента с логикой диалога и **самосохранения**
- `AgentSettings` — настройки агента (провайдер, модель, температура, etc.)

**Важно:** Агент инкапсулирует логику сохранения своего состояния. Use cases не должны явно вызывать репозитории для сохранения агента — агент делает это сам через механизм автосохранения.

#### 8. `context_strategies.py` — Стратегии управления контекстом
Стратегии отвечают **только** за управление контекстным окном: какие
диалоговые сообщения отправить в LLM и какое саммари к ним добавить. Всё
подмешивание памяти, профиля задачи и фазы — ответственность `PromptBuilder`.

**Интерфейс:** `ContextWindowStrategy.apply(dialogue, llm_provider) -> WindowResult`.
Общая логика стратегий со суммаризацией вынесена в `BaseCompressionStrategy`,
чтобы избежать дублирования.

**Реализации:**
- `DefaultStrategy` — пересылка всех сообщений
- `SummarizationStrategy` — суммаризация истории
- `KeyValueMemoryStrategy` — JSON-суммаризация по ключевым категориям
- `SlidingWindowStrategy` — скользящее окно последних N сообщений

#### 9. `prompt_builder.py` — Единая сборка контекста
**Класс:** `PromptBuilder`.

Единственная точка, где в контекст модели подмешиваются:
- базовый системный промпт (персона чата);
- глобальная память о пользователе;
- память задачи, её предпочтения и инварианты;
- per-chat память задачи диалога (цель, ограничения, термины, уточнения);
- описание текущей фазы агента;
- саммари истории, полученное стратегией управления окном.

`PromptBuilder.build(history, PromptSources, strategy, llm_provider)` формирует
ровно один базовый system-блок в фиксированном порядке и возвращает
`PreparedMessages`. Агент хранит ссылку на `PromptBuilder` и вызывает его из
`continue_dialog`.

#### 10. `storage/task_memory_repository.py` — Память задачи диалога
Гибридная память: существующий `TaskProfile` (общие факты/инварианты) остаётся,
а per-chat `TaskMemory` (цель диалога, ограничения, термины, уточнения) хранится
по `conversation_id` в pickle-файлах `{FILE_STORAGE_DIR}/task_memory/`. Она
подмешивается в system-промпт на каждом сообщении, поэтому цель не теряется в
длинном диалоге. Обновление (`Agent.update_task_memory`) идёт через LLM каждые
N ходов и при сжатии контекста; новые уточнения перекрывают устаревшие.
Ветка (`/branch`) стартует с пустой памятью задачи.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `TASK_MEMORY_ENABLED` | `true` | Глобальный выключатель памяти задачи |
| `TASK_MEMORY_UPDATE_EVERY_N_MESSAGES` | `3` | Как часто обновлять память (в ходах) |
| `TASK_MEMORY_WINDOW_MESSAGES` | `12` | Сколько последних сообщений анализировать |

Просмотр — через `/info`. Профиль задачи (`TaskProfile`) можно привязать только
при создании чата; подробности — в
[`docs/uc/uc-022`](docs/uc/uc-022-task-memory.md).

### Требования к разработке

#### ✅ DO (Делайте)

1. **Выносите новую бизнес-логику в use cases и агента**
   - Любая новая функциональность должна быть реализована как новый use case или расширением существующего
   - Use case должен инкапсулировать всю логику взаимодействия с репозиториями и агентами
   - Специфичные для агента операции следует добавлять в класс агента, либо в его зависимые объекты (стратегии и так далее)
   - **Логика сохранения состояния агента должна быть инкапсулирована в самом агенте**, а не в use cases

2. **CLI слой работает только с use cases**
   - `cli_app.py` должен импортировать только из `use_cases`
   - Запрещены прямые импорты репозиториев, LLM провайдеров, агентов в CLI слое

3. **Используйте фабрику для инициализации**
   - Вся логика создания объектов — в `app_factory.py`
   - CLI получает уже готовые use cases из фабрики

4. **Пишите e2e тесты для новой функциональности**
   - Каждый use case должен быть покрыт хотя бы одним e2e тестом
   - Тесты должны соответствовать спецификации: use case и test case — в `docs/uc/`, интерфейс — в `docs/cli_spec.md`
   - Используйте тестовый режим с помощью переменных окружения с Mock провайдером

5. **Следуйте принципу единственной ответственности**
   - Каждый модуль делает только свою работу
   - main_cli → оркестрация и точка входа
   - app_factory → инициализация
   - cli_app → UI/UX
   - use_cases / agents → бизнес-логика
   - storage/llm_providers → инфраструктура

6. **Агент отвечает за своё сохранение**
   - Метод `Agent.save()` вызывается автоматически при изменениях состояния
   - Параметр `auto_save=True` включен по умолчанию для всех агентов
   - Use cases не должны явно вызывать `repository.update_agent()` — это ответственность агента

7. **Минимизируйте количество запросов к базе данных (ORM)**
   - **Подгружайте все необходимые данные сразу при первом обращении к агенту.** Например, при получении агента из репозитория убедитесь, что все нужные поля и данные загружены сразу. То же самое касается внешних ключей, если связанные объекты реально нужны. 
   - **Избегай лишних join'ов в запросах** Но если не нужны - нельзя допускать лишних join'ов и подгрузки ненужных данных.
   - **Избегайте лишних запросов внутри методов агента.** Если методу `_save_agent_history()` нужен `conversation_id`, он должен быть уже загружен в объекте `Agent` при инициализации, а не запрашиваться отдельно из БД на каждый вызов.
   - **Принцип "один раз загрузить, много раз использовать":** При создании или получении агента через `get_agent()` загрузите все связанные данные одним запросом. Это критично для производительности, особенно в сценариях с частыми операциями записи/чтения.
   - **Проверяйте код на наличие N+1 запросов:** Убедитесь, что циклические операции не вызывают повторных обращений к БД за одними и теми же данными.

#### ❌ DON'T (Не делайте)

1. **Не добавляйте бизнес-логику в CLI слой**
   ```python
   # ПЛОХО: в cli_app.py
   agent = repository.get_agent(agent_id)  # Прямой вызов репозитория

   # ХОРОШО: через use case
   agent = self.use_cases.select_chat.get_agent(agent_id)
   ```

2. **Не импортируйте инфраструктурные зависимости в CLI**
   ```python
   # ПЛОХО: в cli_app.py
   from storage.agent_repositories import PersistentAgentRepository
   from llm_providers import YandexCloudLlmProvider

   # ХОРОШО: только use cases
   from use_cases import UseCasesBundle
   ```

3. **Не создавайте бизнес-объекты напрямую в CLI**
   ```python
   # ПЛОХО: в cli_app.py
   strategy = SummarizationStrategy(non_compressible_count=2, buffer_size=3)

   # ХОРОШО: через use case
   selection = StrategySelection(strategy_type="SummarizationStrategy", ...)
   strategy = self.use_cases.select_strategy.execute(selection)
   ```

4. **Не смешивайте режимы работы в CLI**
   ```python
   # ПЛОХО: в cli_app.py
   if os.environ.get("APPLICATION_MODE") == "TEST":
       provider = MockLlmProvider()

   # ХОРОШО: фабрика скрывает эту логику
   use_cases = initialize_application()  # Фабрика сама определит режим
   ```

5. **Не создавайте соединения с БД в репозиториях**
   ```python
   # ПЛОХО: в репозитории
   class PersistentAgentRepository:
       def __init__(self, db_path):
           self.engine = create_engine(f"sqlite:///{db_path}")


   # ХОРОШО: репозиторий получает фабрику сессий
   class PersistentAgentRepository:
       def __init__(self, session_factory):
           self._session_factory = session_factory
   ```

6. **Не вызывайте repository.update_agent() из use cases для сохранения агента**
   ```python
   # ПЛОХО: в use case
   class SendMessageUseCase:
       def execute(self, agent, message):
           response = agent.continue_dialog(message)
           self.repository.update_agent(agent)  # ❌ Явное сохранение


   # ХОРОШО: агент самосохраняется
   class SendMessageUseCase:
       def execute(self, agent, message):
           response = agent.continue_dialog(message)  # ✅ Агент сам сохранит
           return response, agent
   ```

7. **Не делайте лишние запросы к БД при работе с ORM**
   ```python
   # ПЛОХО: conversation_id запрашивается из БД на каждый вызов метода
   class Agent:
       def _save_agent_history(self, messages):
           # ❌ Отдельный запрос к БД внутри метода
           conv_id = self._repository.get_conversation_id(self.id)
           self._chat_storage.save(conv_id, messages)

   # ХОРОШО: conversation_id загружен один раз при инициализации агента
   class Agent:
       def __init__(self, ..., conversation_id: UUID):
           self._conversation_id = conversation_id  # ✅ Загружено заранее

       def _save_agent_history(self, messages):
           # Использует уже загруженное значение без запроса к БД
           self._chat_storage.save(self._conversation_id, messages)

   # В репозитории - загрузка всех данных одним запросом:
   def get_agent(self, agent_id: int) -> Agent:
       with self._session_factory() as session:
           db_agent = session.query(AgentORM).filter_by(id=agent_id).first()
           # ✅ Возвращаем агента со всеми данными, включая conversation_id
           return Agent(id=db_agent.id, conversation_id=db_agent.conversation_id, ...)
   ```

8. **Не ходите в Ollama в обход `llm_gateway` и не масштабируйте его**
   - В PROD/LOCAL обращения к Ollama (чат, эмбеддинги, список моделей) должны
     идти только через `llm_gateway` — иначе нарушается сериализация запросов
   - Держите ровно **одну** реплику/одного потребителя очереди gateway: при
     нескольких потребителях гарантия «один запрос в Ollama одновременно»
     теряется
   - В `APPLICATION_MODE=TEST` шлюз не нужен — там работают mock-провайдеры

### Добавление новой функциональности

Пошаговый процесс добавления новой фичи:

1. **Спецификация**
   - Создайте файл use case в `docs/uc/`: альтернативные потоки и test cases
   - Зарегистрируйте его в таблице-индексе в `docs/cli_spec.md`

2. **Напишите тесты**
   - Добавьте test case в соответствующий файл use case в `docs/uc/`
   - Реализуйте e2e тест в `cli_tests/` (отдельный файл на класс тестов)
   - Запустите тесты: `pytest cli_tests/ -v`. Все тесты, кроме нового, должны пройти

3. **Определите use case**
   - Создайте новый класс в `use_cases.py` или используйте существующий
   - Реализуйте метод `execute()` с необходимой бизнес-логикой

4. **Добавьте use case в Bundle**
   - Обновите `UseCasesBundle` в `use_cases.py`
   - Добавьте поле для нового use case

5. **Инициализируйте в фабрике**
   - В `app_factory.py` создайте экземпляр use case
   - Передайте его в `UseCasesBundle`

6. **Используйте в CLI**
   - В `cli_app.py` вызовите `self.use_cases.<new_use_case>.execute(...)`
   - Обрабатывайте результат и отображайте пользователю

7. **Проверка**
   - Запустите тесты: `pytest cli_tests/ -v`. Все тесты должны пройти
